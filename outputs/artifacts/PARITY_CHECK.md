# Parity Check Report

## Purpose

Verify that the training path (batch, many customers) and the scoring path (single customer,
same as-of date) produce identical feature values for the same customer — the single most
important guarantee for this pipeline.

## Shared Code Path

Both paths call the same function: `features.build.build_features(as_of, ...)`.

- **Training path**: `customer_ids=None` → all 1,500 customers.
- **Scoring path**: `customer_ids=[n]` → single customer.

The only allowed difference is which rows are selected at the end. All transforms run
identically in both cases, with `as_of` threaded through as a parameter.

## Verification Results

### Direct Parity Test

`test_parity.py::test_training_and_scoring_paths_agree_for_same_customer`

Tested customers: 1, 2, 58, 100, 500 (chosen to span zero-activity, high-activity, and
mid-range profiles).

**Result: PASSED** — all feature values matched exactly (float comparison to 1e-6 tolerance,
integer exact match) for every tested customer across all 7 features.

### Zero-Activity Parity Test

`test_parity.py::test_parity_zero_activity_customer`

Tested customer_id=1 (81-customer zero-activity cohort member).

**Result: PASSED** — all default values (tenure_days, 0, 0.0) identical between both paths.

## Parity Mutation Check

To verify the parity test is genuinely load-bearing (not a false positive), a deliberate
training/scoring split was introduced: a second version of `gross_spend_lookback` was
defined with a subtly different return value format for the scoring path. The parity test
was re-run and confirmed to catch the mutation.

**Result: Parity test catches training/scoring splits.** The test is not a false positive.
